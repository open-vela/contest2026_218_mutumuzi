## 2、摘要

本作品在润芯微 Gemini-S1（全志 R528 双核 Cortex-A7，128MB SPI NAND）真机上，完整落地了一套端侧 AI Agent：每天早上 08:00 由板载定时任务自主触发，读技能、查实时天气、读用户健康记忆、调用大模型生成简报并推送上屏，全程无人值守，在 2026-09-07~09-08 期间连续多轮真机验证通过；本轮（09-19）受 LLM 工具调用稳定性影响，多次尝试中成功一次。系统具备多 LLM 路由框架（实现自动失败转移与指数退避，当前部署为单后端未触发实际切换）、10 个板端技能文件的加载与哈希热刷新机制、会话与健康记忆持久化，以及 CLI / BLE GATT / 飞书 / 微信四类渠道的适配层共用同一 Agent 内核（**其中 CLI 端到端验证充分；BLE 广播正常但手机侧端到端未验证；飞书/微信为代码就绪，未配置凭证**）。语音侧打通了云端语音合成与播放出声链路（实测单次合成 88832 字节音频，经 mediad 音频图播放并经耳机实听确认），录音链路实测 1855 个数据块、396144 字节并干净收尾。工程上定位并修复了 7 类固件级缺陷，其中"播放结束即导致 mediad 进程被断言终止"一处根因位于 openvela 音频框架的 link status 契约违反，修复后连续 5 轮录音/播放压测进程全程存活。全部改动以补丁形式交付，公共仓零改动。

## 3、正文

### 3.1 绪论

**项目背景与问题定义**

面向独居老人与慢病人群的健康助理设备。该人群的真实痛点不是"缺少一个能对话的 AI"，而是三件事：

1. **不会主动用**：不习惯操作 App、不识字或视力不佳，需要主动唤醒的语音助手形同虚设；
2. **信息被动缺失**：天气变化、用药提醒、健康趋势这类信息，用户自己想不到主动去查；
3. **隐私与网络顾虑**：健康数据全部上云的方案在用户心理上难以接受；且乡镇与老旧小区网络覆盖不稳定。

因此产品定义的关键不是"能对话"，而是**"不用主动问，它自己会提醒"**——设备需要具备端侧自治能力。

**技术难点**

在 128MB NAND + 双核 Cortex-A7 的资源约束下，把一套完整的 Agent 栈压进端侧，需攻克：

1. **端侧自治调度**：定时任务须在无人干预下完整驱动「读文件 → 调工具 → 调 LLM → 渲染上屏」的长链路；
2. **多媒体链路的稳定性**：音频链路涉及 mediad 守护进程、pfw 策略框架、libavfilter 音频图三层，任一层状态机错误都会导致进程级故障；
3. **云/端职责切分**：语音合成、识别、LLM 在云侧，采集、播放、调度、存储、渲染在端侧，需在断网/弱网下可降级；
4. **异构音频格式的贯通**：云端 TTS 输出 24kHz 单声道，而板级音频图要求 48kHz 立体声，框架不做自动转换。

**创新点**

- **场景创新**：把"主动性"作为第一性设计——零操作、被动接收，而非又做一个需要唤醒的语音助手；
- **技术落地**：端侧 Agent 栈（技能热刷新 + 记忆持久化 + 多渠道 + 多 LLM 路由）在真机上的完整落地，而非裁剪版 Demo；
- **系统性排障**：从 1.5Mbps 串口日志中定位到 openvela 音频框架的契约违反这一非直观根因，体现了从产品到内核的纵向能力。

**数据流（早间简报，全自动）**

```
08:00 cron 触发
  → Agent 内核装载会话上下文（SOUL / USER / MEMORY + 技能摘要）
  → 调用 LLM（携带工具定义）
  → LLM 决定调用工具：get_current_time → get_weather(Tavily 检索)
  → 工具结果回灌 → 再次调用 LLM 生成简报
  → 简报经 mqueue 推送至 LVGL 通道 → 卡片上屏刷新
```

**方案论证与选型**

| 决策点 | 选择 | 理由 |
|---|---|---|
| 开发板 | 润芯微 Gemini-S1（全志 R528） | 大赛指定真机；双核 A7 + 128MB NAND 足以承载 Agent 栈，又能暴露资源约束下的真实工程问题 |
| 系统 | openvela / NuttX 实时操作系统 | 大赛专属分支；相比 Linux 具备更低的启动延迟与内存占用，且多媒体框架（mediad）提供了结构化的音频图能力 |
| 端/云职责 | 采集、播放、调度、存储、渲染在端；识别、合成、推理在云 | 端侧算力不足以跑语音与 LLM 推理；但调度与数据留在端侧，保证断网时设备仍可工作、隐私数据不出本地 |
| LLM | 多后端路由框架（实测使用过 MiMo 与 DeepSeek 两个后端，但为**手动切换**） | 路由层已实现自动失败转移与指数退避；当前部署仅配置单后端，自动切换路径未实测 |
| 音频输出 | 板载 3.5mm 耳机孔 | HS 板载仅麦克风，无扬声器 |

**断网/弱网降级策略（设计，未单独测试）**：网络监视线程感知链路状态；LLM 多后端路由在单个后端失败时切换并计数退避；云侧调用失败时保留端侧既有数据（记忆、定时任务）不受影响，简报保留上一次内容不刷新。**说明**：组件均已实现并有代码路径，但未构造断网场景做端到端验证。

**关键模块设计**

- **Agent 内核**：消息总线（深度 16）解耦各通道；工具注册表统一管理 20+ 内置工具；工具守卫限制单次输入 ≤32KB、速率 10 次/60 秒，防止工具被滥用导致资源耗尽。
- **技能系统**：技能以 Markdown 文件形式落 `/data/ai_agent/skills/`，启动时扫描并计算文件哈希，哈希变化即刷新技能摘要。**说明**：技能文件的加载与摘要刷新已验证；但**运行时热刷新路径历史上出现过崩溃记录**（skill 文件变更后触发任务），本轮未复现，标记为待排查。
- **语音通道**：录音走 mediad 的 media_recorder（PCM 采集），合成走云端 TTS，播放走 mediad 的 media_player；三者的会话生命周期由状态机串行化，避免并发占用音频图。
- **多渠道**：CLI（stdin）、BLE GATT (NUS)、飞书、微信共用同一 Agent 内核，差异仅在输入/输出的适配层。**验证状态**：CLI 端到端充分验证；BLE 服务注册与广播正常（`advertising started OK`），手机侧命令端到端未验证；飞书/微信代码就绪，因无凭证未启用。

### 3.3 核心算法与技术原理

**AI 算法实现**

| 环节 | 位置 | 实现 |
|---|---|---|
| 语音识别 ASR | 云端 | 火山引擎 v3（`/api/v3/sauc/bigmodel_async`），流式二进制帧协议：帧头 `[0x11, msg_type, serialization, 0x00]` + 4 字节长度 + 载荷；消息类型 `0x10` 全量请求 / `0x20` 音频 / `0x22` 音频结束；服务端 PING 控制帧须回 PONG |
| 语音合成 TTS | 云端 | 火山引擎 V3（WebSocket 流式），资源号 `seed-tts-2.0`，音色 `zh_male_m191_uranus_bigtts`；单次请求实测返回 13 个音频块，首块时延 1332ms，网络总耗时 5181ms |
| LLM 推理 | 云端 | OpenAI 兼容接口，鼓励使用大赛 MiMo（本项目主力后端为 `mimo-v2.5-pro`，备用为 `deepseek-chat`）。鉴权走 `Authorization` 头；请求携带工具定义（function calling） |
| 实时检索 | 云端 | Tavily 检索 API，用于早间简报的天气与新闻事实性来源 |

端侧不承担模型推理，职责为：音频采集与重采样、音频播放、任务调度、上下文装配、结果渲染。这一划分的依据是端侧算力（双核 A7、无 NPU）与内存（可用堆约 900MB 虚拟区、实际物理 128MB NAND 约束）的客观限制。

**关键机制设计**

1. **多 LLM 路由**：每个后端维护失败计数与退避窗口；调用失败时自动切换至下一可用后端，并记录 `backend=N llm=fail` 的追踪事件，便于事后归因。
2. **工具守卫（Tool Guard）**：限制单次工具输入 ≤32KB、调用速率 10 次/60 秒，防止长文本或工具风暴耗尽端侧内存。实测堆使用稳定在约 2.9MB。
3. **会话串行化**：语音录音与播报通过互斥锁串行化，播报期间拒绝新的录音请求，避免两个媒体会话同时占用音频图——这正是历史上导致 mediad 崩溃的场景之一。**说明**：互斥逻辑在代码中实现；本轮实测中未主动构造并发场景验证。
4. **配置原子更新**：`llm` 配置变更采用原子更新（`LLM config updated atomically`），避免运行中读到半更新的配置。

**openvela 系统能力的深度运用**

明确落地的能力：**多媒体**（核心）、**图形**、**AI 框架与工具链**。

| openvela 组件 | 运用方式 |
|---|---|
| `mediad` 多媒体守护进程 | 音频采集与播放的会话管理 |
| `pfw` 策略框架 | `criteria.txt` 定义音频流策略（独占、音量域） |
| `audio_graph` | `graph.conf` 描述音频拓扑，运行时动态 link/unlink |
| `libavfilter` 音频图 | `adevsrc`/`adevsink`/`abufsrc`/`abufsink`/`amix`/`volume` 六类滤镜 |
| LVGL | 简报卡片渲染与上屏 |
| BLE GATT (NUS) | 手机侧命令通道（服务与广播已验证，端到端待验证） |
| cron 服务 | 定时任务持久化调度 |

**对 openvela 的优化/拓展与改进建议**（均为真机日志定位，补丁见 `docs/`）：

1. **libavfilter link status 契约缺少守卫，缺陷后果为进程级终止**。`ff_inlink_request_frame()` 的契约（`libavfilter/filters.h:384`）要求"不得在 link 已有非零 status 时调用"，但 `asink_adevsink.c` 与 `asink_abufsink.c` 均无条件调用。上游 `abufsrc` 的 `unlink` 会给该 link 打上 EOF，下一次 `activate` 即触发 `Assertion !status_in failed at avfilter.c:1760`，**整个 mediad 进程被终止**（现场表现为"板子像死机"）。建议把状态检查下沉到 `ff_inlink_request_frame()` 内部改为静默忽略，或至少在框架文档中标注该契约的违反后果。本项目已按同目录 `asink_alsasink.c` 的既有写法在两处 sink 补齐守卫。
2. **`ff_inlink_acknowledge_status()` 的三态返回值容易被误用**：首次确认到状态时返回 `1`（非负数），此后返回状态本身。`asink_abufsink.c` 原先只判 `if (ret < 0) continue;`，首次 EOF 时掉入后续请求并触发同一断言。建议在头文件注释中显式说明。
3. **NuttX local socket 接受 `SO_RCVTIMEO` 但不使用**：AF_UNIX 上 `setsockopt` 会接受该选项，但本地 socket 路径从不读取，导致 `recv()` 永久阻塞。建议返回 `ENOPROTOOPT` 而非静默接受。
4. **音频图不做格式自动转换**：`adevsink` 遇 `ch_layout` 变化直接报 `Channel layout change is not supported` 并中断协商。建议在文档中明确该约束。
5. **注入型上下文的编码完整性缺少校验**：本项目遇到一次典型案例——配置目录中的 `SOUL.md`（人格设定文件）在 256 字节处被截断，最后一个汉字仅存留了 3 字节 UTF-8 序列中的前 2 字节。该文件被注入为 system prompt 后，**整个请求体变为非法 UTF-8**，云端返回 `API error 400: invalid unicode code point at line 1 column 3948`，表现为 LLM 全部调用失败。根因分析路径为：错误码中的列号 → 定位到 system prompt 区段 → 逐文件字节校验 → 发现尾部残缺序列。**建议**：文件注入环节应对每个文件做 UTF-8 完整性校验并在截断处按字符边界回退，而非按字节截断。

### 3.4 系统实现

**软件/固件架构**

- **应用层**：`packages/ai_agent`——Agent 内核、技能系统、工具集、多渠道适配、语音通道、LVGL UI 通道；
- **多媒体层**：openvela `frameworks/multimedia/media`（mediad / pfw / audio_graph）+ 定制 libavfilter 滤镜；
- **板级层**：`vendor/allwinnertech/boards/r528/r528s3-gemini-s1`（defconfig、`/etc` 配置源、启动脚本）；
- **配置源注意点**：`/etc` 的固件打包源为 `src/etctmp/etc/` 而非 `src/etc/`，且 `src/etctmp.c` 为生成物，修改后必须删除才会重新生成——这是本项目 mediad 配置长期不生效的根因。

**数据流与关键流程**

语音播报流程：

```
调用方（对话回复 / CLI voice_speak）
  → 火山 TTS WebSocket 建立 → 请求文本（UTF-8）
  → 分块接收 PCM（24kHz 单声道）
  → 重采样为 48kHz + 单声道复制为立体声
  → media_player 写入（首块到达时才启动播放器，避免空流被判定 EOF）
  → mediad 音频图：abufsrc → volume → adevsink → /dev/audio/pcm0p
  → sunxi-codec → 3.5mm 耳机孔输出
  → 会话 stop → unlink → close → 播放器线程退出
```

**硬件设计与适配**

- **开发板**：润芯微 Gemini-S1（全志 R528 / sun8iw20，双核 Cortex-A7，128MB SPI NAND，2.8" SPI LCD，RTL8723 WiFi+BT，sunxi-codec）
- **外接**：3.5mm 耳机（音频输出）；USB（adb 调试）；UART2（串口控制台，1.5Mbps）
- **是否完成全新硬件平台适配或驱动开发**：**是**
- **驱动类型**：音频（sunxi-pcm + DMA）、显示（SPI LCD）、存储（SPI NAND）、无线（SDIO WiFi/BT）

**适配难点与解决方案**：

| 难点 | 现象 | 解决方案 |
|---|---|---|
| mediad 无法启动 | 白屏；mediad 进程不存在（持续 17 天） | 三层叠加：`criteria.txt` 中 8 处判据名重复 → pfw 判重报错；`MuteMode` 判据缺失；`alsasink` 未编入固件。逐一修复 |
| `/etc` 改动不生效 | 固件内配置与源码不一致 | 打包源为 `src/etctmp/etc/`；须删除生成物 `src/etctmp.c` |
| 编译缓存陷阱 | 修改头文件后行为不变 | 构建系统不跟踪头文件依赖，须手工清理相关 `.o` |
| 播放结束即崩溃 | mediad 整体消失 | libavfilter link status 契约违反（见 3.3） |
| 录音停止死锁 | 停止录音后线程永不退出 | 改用 `poll()` 前置检查绕开 `SO_RCVTIMEO` 失效 |
| 音频格式不匹配 | `Channel layout change is not supported` | 在应用层按 sink 格式（48kHz 立体声）开播放器，并做线性插值重采样与声道扩展 |

**应用/交互端设计**

- 板载 launcher 提供时间、温湿度、距离等常驻信息；
- 简报通过 mqueue 推送至 LVGL 卡片上屏；

**补充说明**：

*效率提升*：
1. **串口日志归因**：真机每秒数十条 syslog，人工很难从 1.5Mbps 串口流中做因果链追溯。AI 把"断言地址 → 源码行 → 调用链 → 框架契约文档"一次性串起，mediad 崩溃这个卡了数天的问题从拿到日志到定位根因仅用数轮对话；
2. **会话式真机调试**：AI 直接驱动板端命令、解析回显、迭代验证；
3. **产出一致性**：根因分析、补丁、文档由同一上下文产出，避免"修完忘了为什么修"。

*遇到的问题与解决方式*：
1. **AI 基于错误前提连续下判断**：曾把测试工具 `mediatool` 自身的缺陷（`close` 命令因缓冲区线程卡死而未执行，造成"图槽位泄漏"假象）误判为 mediad 缺陷，连续两版固件改错位置。**解决**：确立"先复现、先看进程列表与原始日志，再动手改"的纪律，并将教训写入跨会话记忆；
2. **板端 CLI 与控制台争抢输入**：`nsh` 与 Agent CLI 逐字符争抢同一行，命令被切碎（`help` → `hep`/`ple`）。**解决**：改用 SSH 管道向 CLI 喂 stdin；
3. **板端中文输入编码**：adb shell 下中文以 GBK 传出，云端 TTS 返回 `45002001: No readable text!`。**解决**：Windows 侧 `chcp 65001` 后再进入 adb shell。

### 3.7 总结与展望

**成果总结**

在真机上完整落地了一套端侧 AI Agent 与语音链路：全自动早间简报（多轮无人值守验证）、10 个技能的热刷新、多 LLM 路由、四类交互渠道、语音合成与播放出声（实听确认）、录音链路（实测 1855 块 / 396144 字节）。工程层面定位并修复 7 类固件级缺陷，其中 openvela 音频框架的 link status 契约违反属于进程级故障，修复后连续 5 轮压测稳定。全部改动以补丁交付，公共仓零改动，其中 HTTP chunked 读取修复已提公共仓 PR #27。

**应用前景与商业价值**

*目标受众*：独居老人、慢病患者及其子女。主要使用者 60–80 岁，实际购买决策者多为 30–50 岁的子女；地域上集中在一二线城市独居老人（子女异地）与网络覆盖不稳定的三四线城市、乡镇；使用偏好为语音优先、被动接收、隐私敏感。

*商业模式*：硬件一次性销售 + 云服务订阅（LLM 与语音合成的用量）。核心成本项为语音与推理的云端调用，可通过端侧缓存与请求合并优化。规模化潜力在于：设备形态轻（无需屏幕交互能力即可使用）、部署门槛低（单板 + 云端）、可复用到养老机构与社区健康服务场景。

**不足与未来工作**

1. **流式播报链路未打通**：`voice_speak` 在流式喂数据时播放器 xrun，音频被拒。下一步需在播放层引入预缓冲或欠载恢复机制；
2. **语音识别与完整对话闭环待端到端验证**；
3. **LLM 看门狗超时**：配额受限或模型响应慢时触发 60s 看门狗，且板子无 RTC，时钟跳变会放大误判，需改用单调时钟计量；
4. **语音按钮 UI 未启用**：`ui/lvgl_ui_channel.c` 含完整 PTT 实现（112px 圆形"请说"按钮），受 `CONFIG_AI_AGENT_LVGL_UI` 控制；该开关启用后构建失败，且界面按圆形表盘设计，需适配方形屏；
5. **天气检索质量**：Tavily 页面解析处于"可用但待打磨"状态。
