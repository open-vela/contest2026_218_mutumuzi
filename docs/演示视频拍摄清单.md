# 演示视频拍摄·操作流程（≤5 分钟）

> **本流程的每一步都已在真机验证过。** 按顺序做即可。
> 拍摄原则：**只拍已经验证过的功能。**

---

## 〇、窗口准备

开 **3 个东西**：

| 编号 | 是什么 | 用途 |
|---|---|---|
| **窗口 A** | Windows 命令提示符（cmd） | 驱动板子的 AI Agent（合成语音） |
| **窗口 B** | 另一个 Windows cmd | 驱动板子播放音频 |
| **相机** | 手机，横屏 1080p，三脚架 | 拍板子屏幕 + 耳机出声 |

**耳机**：一只戴耳朵里，**另一只留着贴手机麦克风**（用胶带固定）。

---

## 一、开拍前准备（务必先做，逐条核对）

### 1.1 板子开机后，在**窗口 A** 里跑

```
chcp 65001
```

> ⚠️ **这一步绝对不能省。** 板端中文必须 UTF-8，否则 TTS 会报
> `TTS error 45002001: No readable text!`（我们踩过这个坑）

```
adb shell
```

进入 nsh 后：

```
wapi psk wlan0 kobe0824 3
wapi essid wlan0 oldbig 1
renew wlan0
date -s "Sep 19 18:00:00 2026"
ifconfig
```

> `date` 必须设（板子无 RTC，时间太偏会导致 TLS 握手失败）

### 1.2 确认素材文件在

```
ls -l /data/speak.pcm
```

**必须显示 `352256`**。如果显示不出来或数字不对 → **停下来找我**，别开拍。

### 1.3 试音（关键！）

按下面「二、正式拍摄」的 **步骤 2** 完整跑一遍，确认耳机出声、手机能录到。
**不成不拍。**

## 二、正式拍摄

### 🎬 镜头 1 · 开篇（0:00–0:20）

- **相机**：板子特写，缓慢推近
- **无需操作**

**旁白**：
> 「这是润芯微 Gemini-S1，全志 R528 双核 Cortex-A7，128MB SPI NAND。
> 它跑的不是 Linux，是 openvela——面向 AI 硬件的实时操作系统。
> 我们要在它上面，跑一个会自己干活的 AI 健康守护官。」

---

### 🎬 镜头 2 · 开机与常驻界面（0:20–0:50）

- **相机**：屏幕正面特写
- **操作**：断电 → 上电 → 等 15~20 秒 launcher 出现

**旁白**：
> 「开机。常驻界面：时间、环境温湿度、距离感应。这些是板载原生能力，也是我们 AI 服务的载体。」

**验收**：屏幕上的**时间数字在跳动**（证明不是截图）

---

### 🎬 镜头 3 · ★语音合成（0:50–1:40）

**窗口 A**（此时应该在 `nsh>`，如果不在就敲 `exit` 退回来）：

```
ai_agent
```

等 15 秒，看到 `AI Agent ready`，然后敲：

```
voice_test_tts 您好，我是您的健康守护官，今天天气不错，记得按时吃药
```

**屏幕上会滚出**：

```
TTS: synthesizing "您好，我是您的健康守护官……" ...
TTS OK: 88064 bytes -> /data/ai_agent/tts_out.pcm
```

- **相机**：对准屏幕，拍下这段文字滚出

**旁白**：
> 「这段语音不是预录的。板子实时调用云端语音合成，把文字变成音频数据。」

**验收**：屏幕上出现 `TTS OK: 88064 bytes`

---

### 🎬 镜头 4 · ★★ 平板出声（1:40–2:40）

**这是全片最关键的一镜。**

**窗口 B** 里：

```
adb shell
```

然后敲（**逐行敲，每行回车**）：

```
mediatool
```

看到 `mediatool>` 提示符后，**逐行**敲：

```
open Music
```

```
prepare 0 buffer /data/speak.pcm format=s16le:sample_rate=48000:ch_layout=stereo
```

```
start 0
```

**▶ 这时耳机出声** —— 相机对准耳机/音箱，录下声音。

**等声音播完**（约 15 秒），再敲：

```
q
```

- **相机**：先拍屏幕上的 `PREPARED → STARTED`，声音出来时**镜头转向耳机**（或一镜到底拍板子+耳机）

**旁白**：
> 「音频经 openvela 的多媒体框架 mediad 播放，走音频图和编解码器，最终从扬声器输出。
> 合成、播放，全部在真机上完成。」

**验收**：**手机录到了语音**

> ⚠️ **注意事项**
> - `prepare` 那行很长，**如果敲进去被截断**（提示 `Unknown cmd`），就在板子上用
>   `mediatool` 时**分两次**：先敲 `open Music`，确认成功了再敲下一行
> - **mediad 每次开机只能播一次**（测试工具 mediatool 的已知缺陷）。
>   **要重拍就重启板子**，然后重跑「一、开拍前准备」

---

### 🎬 镜头 5 · 语音识别（2:40–3:20）

**窗口 A**（`vela>` 提示符）：

```
voice_start
```

对着麦克风说 3~5 秒（比如"今天天气怎么样"），然后：

```
voice_stop
```

**屏幕上会出现**：

```
Voice: recording... (use voice_stop to finish)
[voice] recording thread exit: NNNN chunks, NNNNN read
```

- **相机**：拍屏幕上的录音日志

**旁白**：
> 「语音采集同样在端侧完成：板载麦克风采样、编码，通过流式语音识别转成文字。
> 录音链路已完整打通。」

**验收**：屏幕上出现 `recording thread exit: ... chunks`

> ⚠️ 如果 `voice_stop` 后**没有**出现录音统计行，说明这条重录一次；
> 再不成，**跳过这一镜**，别纠缠。

---

### 🎬 镜头 6 · 架构与排障（3:20–4:20）

**纯电脑录屏**，不需要板子。

- **画面**：左边放音频图拓扑示意图，右边放串口日志

**旁白**：
> 「真正的难点不在调用 AI，在让它于资源受限的真机上稳定运行。
> 我们遇到最硬的一个问题：**每次播放结束，整个 mediad 进程会被断言打死**。
> 从串口日志看到 `Assertion !status_in failed`——顺着这条线查下去，
> 是 openvela 音频滤镜里，上游已经给数据流打了结束标记，下游却还在请求数据，
> 违反了框架的契约。**这不是返回一个错误，是整个进程终止**，所以现场表现是「板子像死机」。
> 我们按框架同目录的既有写法补齐了守卫。修复之后连跑五轮录音播放，进程全程存活。」

**画面素材**（都在 `docs/` 里）：
- `fixes-summary-20260919.md` 第一节的因果链
- `firmware-fixes-avfilter-assert-20260919.patch` 的 diff（前后对比）
