## 1、产品概述

**产品名称**：木木 · Gemini-S1 AI 随身健康守护官

**一句话介绍**：在润芯微 Gemini-S1（全志 R528，128MB SPI NAND）真机上，把一套完整的端侧 AI Agent 栈——多 LLM 路由、技能系统、定时调度、语音合成与播放、多渠道送达——完整压进一颗双核 Cortex-A7。

**应用场景**：面向独居老人与慢病人群的随身健康助理。这类用户的核心诉求不是"能问 AI"，而是"不用主动问，它自己会提醒"——每天早上自动生成一份包含健康提醒、天气、日程的简报并推送，全程无人值守；支持语音交互（说出需求→识别→理解→语音播报回复），不需要识字、不需要操作 App；设备断网可重连，健康数据落本地存储重启不丢。

解决的行业痛点：现有健康类智能设备要么是"哑终端 + 云端 App"（隐私外流、断网即废），要么把 AI 能力做成需要主动唤醒的语音助手（老人不会用）。本作品把**主动性**（定时自治）与**端侧 Agent**（技能/记忆/多渠道）结合，让设备"自己会干活"。

**创新功能与体验亮点**：
- **全自动早间简报**：每天 08:00 由板载定时任务触发，AI Agent 自主完成「读技能 → 查时间/天气（实时检索）→ 读用户档案与健康记忆 → 调用 LLM 生成简报 → 推送上屏」，已连续多轮真机验证，全程无人值守。
- **端侧 Agent 栈完整落地**（非 Demo 级调用）：多 LLM 路由（含失败转移与退避）、10 个技能的文件哈希热刷新、会话与健康记忆持久化、CLI / BLE GATT / 飞书 / 微信四类渠道共用同一 Agent 内核。
- **语音合成与播报链路打通**：真实调用云端 TTS 合成（实测单次产出 88832 字节音频），经 openvela 多媒体框架 mediad 的音频图播放出声，耳机实听确认；录音链路实测 1855 个数据块、396144 字节，停止后干净收尾。
- **工程排障**：白屏、mediad 音频栈进程级崩溃、蓝牙栈溢出、HTTP chunked 响应截断等问题全部从串口日志定位到根因并修复，共 7 类固件级缺陷，其中"播放结束即导致 mediad 进程被断言终止"一处根因位于 openvela 音频框架的 link status 契约违反（进程级故障），修复后连续 5 轮压测进程全程存活。

## 2、openvela 系统能力运用

**运用情况**：

- **多媒体框架（media framework）**：完整使用 `mediad` 守护进程 + `pfw` 策略框架 + `audio_graph` 音频图。通过 `criteria.txt` 配置音频流策略（独占总线、音量域），通过 `graph.conf` 描述音频拓扑。
- **libavfilter 音频图**：使用自定义滤镜 `adevsrc` / `adevsink`（设备源/汇）、`abufsrc` / `abufsink`（缓冲区源/汇）、`amix`（混音）、`volume`，搭建「采集设备 → 音量 → 缓冲汇」与「缓冲源 → 音量 → 播放设备」两条链路。
- **BLE GATT (NUS)**：板端 BLE 服务，支持手机下发命令。
- **定时调度**：cron 服务持久化到 `/data/ai_agent/cron.json`，重启保留。
- **板级裁剪**：通过 defconfig / Kconfig 控制固件组成（mediad、alsasink、LVGL 等）。
- **NuttX 驱动栈**：sunxi-pcm 音频驱动、DMA、SPI NAND、RTL8723 WiFi/BT。

**改进建议（均为真机日志定位，补丁见 `docs/`）**：

1. **libavfilter 的 link status 契约缺少守卫，缺陷后果是进程级崩溃**。`ff_inlink_request_frame()` 的契约（`libavfilter/filters.h:384`）明确要求"不得在 link 已有非零 status 时调用"，但 `asink_adevsink.c` 与 `asink_abufsink.c` 均无条件调用。当上游（如 `abufsrc` 的 `unlink`）已给该 link 打上 EOF 后，下一次 `activate` 即触发 `Assertion !status_in failed at avfilter.c:1760`，**整个 mediad 进程被终止**（不是返回错误）。建议把状态检查下沉到 `ff_inlink_request_frame()` 内部改为静默忽略，或至少在框架文档中标注"违反该契约会导致进程终止"。我们已按同目录 `asink_alsasink.c` 的既有写法在两处 sink 补齐守卫。
2. **`ff_inlink_acknowledge_status()` 的三态返回值容易被误用**。该函数**首次**确认到状态时返回 `1`（不是负数），此后返回状态本身。`asink_abufsink.c` 原先只判 `if (ret < 0) continue;`，导致首次 EOF 时掉进后续的 `ff_inlink_request_frame()`，触发同一个断言。建议在头文件注释中显式说明该返回值语义。
3. **NuttX local socket 接受 `SO_RCVTIMEO` 但不使用**。AF_UNIX 上设置该选项会被 `setsockopt` 接受，但本地 socket 代码路径从不读取它，导致 `recv()` 永久阻塞。建议在 `setsockopt` 处返回 `ENOPROTOOPT` 而非静默接受。
4. **音频图不做格式自动转换**。`adevsink` 对 `ch_layout` 变化直接报 `Channel layout change is not supported` 并中断协商。建议在文档中明确"图内不做 mono↔stereo 与采样率转换，调用方须按 sink 格式提供数据"。
5. **注入型上下文的编码完整性缺少校验**。本项目遇到典型案例：人格设定文件 `SOUL.md` 在 256 字节处被截断，最后一个汉字仅存留 3 字节 UTF-8 序列中的前 2 字节；该文件注入 system prompt 后**整个请求体变为非法 UTF-8**，云端返回 `API error 400: invalid unicode code point at line 1 column 3948`，表现为 LLM 全部调用失败。建议文件注入环节对每个文件做 UTF-8 完整性校验，并在截断处按字符边界回退，而非按字节截断。

## 3、硬件适配说明

**是否完成全新硬件平台适配或驱动开发**：是

**适配的芯片/开发板型号**：润芯微 Gemini-S1（大赛指定真机）。SoC 为全志 R528（sun8iw20），双核 ARM Cortex-A7；128MB SPI NAND；2.8 英寸 SPI LCD；RTL8723 WiFi + BT；sunxi-codec 音频（板载麦克风，音频输出走 3.5mm 耳机孔）。

**驱动类型**：音频（sunxi-pcm + DMA）、显示（SPI LCD）、存储（SPI NAND）、无线（SDIO WiFi/BT）。

**适配难点与解决方案**：

| 难点 | 现象 | 解决方案 |
|---|---|---|
| mediad 无法启动（持续 17 天） | 白屏，mediad 进程不存在 | 三层原因叠加：① `criteria.txt` 中 8 处判据名重复导致 pfw 判重报错；② `MuteMode` 判据缺失；③ `alsasink` 未编入固件。逐一修复后 mediad 恢复 |
| `/etc` 改动不生效 | 改了 `src/etc/` 但固件里仍是旧内容 | 打包源实为 `src/etctmp/etc/`；且 `etctmp.c` 为生成物，**修改后必须删除才会重新生成** |
| 编译缓存陷阱 | 修改 `.h` 后行为不变 | 构建系统不跟踪头文件依赖，须手工清理相关 `.o` |
| 播放结束即崩溃 | mediad 整体消失，后续所有媒体操作失败 | libavfilter link status 契约被违反（详见第 2 节第 1 条） |
| 录音停止死锁 | 停止录音后线程永不退出 | 改用 `poll()` 前置检查，绕开 NuttX local socket 的 `SO_RCVTIMEO` 失效问题 |

**补充说明——AI 工具对开发效率的提升**：

1. **串口日志归因**：真机每秒数十条 syslog，人工很难从 1.5Mbps 串口流中做因果链追溯。AI 把"断言地址 → 源码行 → 调用链 → 框架契约文档"一次性串起来，mediad 崩溃这个卡了数天的问题从拿到日志到定位根因只用了数轮对话。
2. **会话式真机调试**：AI 直接驱动板端命令、解析回显、迭代验证，省去大量手工敲命令与抄日志的工作。
3. **补丁与文档同步产出**：根因分析、补丁、说明文档由同一上下文产出，避免"修完忘了为什么修"。

**遇到的问题与解决方式**：

- **AI 会基于错误前提连续下判断**：本轮出现过一次误判——把测试工具 `mediatool` 自身的缺陷（其 `close` 命令因缓冲区线程卡死而未执行）当成 mediad 的缺陷，连续两版固件改错了位置。解决方式：确立"**先复现、先看进程列表与原始日志，再动手改**"的纪律，并把这轮教训写入跨会话记忆（`media-debug-pitfalls.md`）避免重蹈。
- **板端 CLI 与控制台争抢输入**：`nsh` 与 AI Agent 的 CLI 逐字符争抢同一行输入，表现为命令被切碎。解决方式：改用 SSH 管道向 CLI 喂入 stdin，稳定可复现。
- **板端中文输入编码**：adb shell 下中文以 GBK 传出导致服务端拒收（云端 TTS 返回 `45002001: No readable text!`）。解决方式：Windows 侧 `chcp 65001` 后再进入 adb shell。
- **云侧模型工具调用格式兼容**：DeepSeek 后端部分请求将工具调用语法以**字面文本**返回（而非结构化 tool_calls），导致依赖工具的请求（如早间简报）失败；MiMo 后端受配额限制。已通过多后端路由缓解，进一步需针对模型调整工具协议适配。

## 5、目标受众分析

| 维度 | 描述 |
|---|---|
| 目标人群 | 独居老人、慢性病（高血压/糖尿病）患者及其子女；以及需要"主动提醒型"AI 助手的健康关注人群 |
| 年龄范围 | 主要使用者 60–80 岁；**实际购买决策者多为 30–50 岁的子女** |
| 地域特征 | 一二线城市独居老人（子女异地工作）；以及网络覆盖不稳定的三四线城市与乡镇 |
| 使用偏好 | 不习惯主动操作 App、不识字或视力不佳，因此偏好**语音优先、被动接收**；对隐私敏感，不希望健康数据全部上云；对"设备自己会提醒"的主动性评价高于"能对话" |

由此推导的产品设计取向：**零操作**（定时自动简报，用户什么都不做也能获得信息）、**语音输入输出**（绕开识字与操作门槛）、**端侧为主**（健康档案与记忆落本地存储，重启不丢）。
